# Командная работа

## Начало работы

Команда закрепляет имена за ролями У1–У5 из [плана](docs/IMPLEMENTATION_PLAN.md). У каждой задачи есть один владелец, проверяемый результат и ревьюер. Обозначения ролей пока не являются назначениями пользователей GitHub.

В трекере используем колонки Backlog, Ready, In progress, Review, Done. В Ready попадают задачи с понятными условиями приёмки и закрытыми блокирующими зависимостями. Одновременно у участника одна основная задача; ожидание ревью не запрещает взять небольшую независимую работу.

## Ветки и изменения

- Основная ветка — `main`.
- Работа ведётся в коротких ветках `feat/Txx-description`, `fix/Txx-description`, `docs/Txx-description`; ветки автоматизированного помощника могут иметь префикс `codex/`.
- Изменения поступают через pull request с номером задачи, описанием результата и проверками.
- Не менее одного содержательного ревью другим участником. Изменения доступа проверяет У2, контрактов — У1, эксплуатации — У5; автор не заменяет независимого ревьюера.
- До первого merge владелец репозитория настраивает доступ команды и, если доступно, защиту `main`: запрет force push, обязательное ревью и проверки. Пока настройки не включены, это правило команды, а не техническая гарантия.
- Контракты и миграции изменяются явно, с согласованием затронутых участников. Готовые совместимые изменения объединяются после ревью и проверок.

## Когда задача завершена

1. Выполнены критерии приёмки задачи и обновлена документация изменённого поведения.
2. Выполнены проверки, соответствующие риску: позитивный сценарий, важные ошибки и запреты доступа.
3. Проверено поведение потребителя: кнопка или команда вызывает реальную операцию, данные сохраняются, уведомления доходят.
4. Есть независимое ревью; обязательные проверки проходят.
5. Миграция и откат описаны, если они нужны. В Git нет токенов, ключей, реальных анкет и фотографий участников.
6. Результат показан на тестовом стенде или воспроизводимо проверен локально, если задача не затрагивает стенд.

## Взаимодействие команды

Участники сообщают о готовых результатах и блокерах. У1 и У5 вместе с владельцами модулей проверяют интеграцию; завершённый этап подтверждается демонстрацией сквозного сценария. Нерешённые блокеры передаются У1. Новые требования получают отдельную задачу, владельца и решение о включении в объём проекта.

Проверка документации не требует запуска приложения, которого ещё нет. Команды установки, запуска и тестов будут добавлены в README в задаче T21 после выбора стека.
