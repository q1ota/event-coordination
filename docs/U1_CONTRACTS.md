# Мероприятия и задания

У1 реализует предметную логику мероприятий, участия и заданий как Python-модуль с постоянным хранилищем SQLite. Пользовательские интерфейсы вызывают этот модуль; ему не нужны мессенджер или внешнее ядро для выполнения бизнес-операций. Регистрация, получение личности из сообщения, проверка согласий и отправка сообщений остаются у У2–У4.

## Решения и границы ответственности

| Решение | Состояние | Владелец и условие принятия |
| --- | --- | --- |
| D01 Платформа чатов | Открыто; доменная логика от платформы не зависит | У4 проверяет создание, приглашение, отзыв и архив на реальном тестовом чате; У1 принимает совместимость с контрактами |
| D02 Стек | Python и SQLite согласованы пользователем | Модуль использует Python 3.12+ и стандартную библиотеку; У5 определяет размещение и хранение вложений при подключении инфраструктуры |
| D03 Согласия и данные | Открыто; модуль не решает правовые вопросы | Заказчик утверждает правила с У2; У2 возвращает допуск только после обязательных проверок |
| D04 Полномочия | Техническая граница определена; реальные назначающие лица не выбраны | Заказчик определяет первого координатора и назначающих лиц; У2 реализует подтверждение и отзыв. В модуле нет самоназначения ролей |
| D05 Уведомления | Маршруты определены; периодичность напоминаний остаётся решением заказчика и У4 | Запрос помощи идёт ответственному, явная эскалация и итоги — координации. Повседневные изменения не отправляются в координационный чат |
| D06 Пилот | Открыто | Заказчик и У5 определяют участников, территории, направления и критерии пилота. Демонстрация на синтетических данных проверяет модуль, но не заменяет пилот |

MVP сохраняет требования R01–R13 и разделение обязанностей из плана. У1 не закрывает за остальных участников регистрацию, бот, доставку уведомлений или реальное архивирование чатов. Решения без ответа заказчика остаются открытыми; зависимая функциональность не выдаёт фиктивное подтверждение успеха.

## Модель и состояния

| Сущность | Владелец | Данные и инварианты |
| --- | --- | --- |
| Identity | У2 | Стабильный внутренний ID, отображаемое имя, актуальный допуск и право общей координации. Не является телеграм-ID или параметром формы с ролью |
| Event | У1 | Название, место, дата с часовым поясом, территория, направление, цель, помощь, автор, состояние, версия, главный ответственный |
| Participation | У1 | Одна запись на пару мероприятия и пользователя; requested, invited, active, rejected или removed |
| Task | У1 | Мероприятие, текст, исполнитель, срок с часовым поясом, состояние, версия, причина запроса помощи или отмены |
| Report и Chat | У4 | Отчёт и реальный чат, результаты доставки и архивирования; У1 получает подтверждения через CompletionReader |
| Command | У1 | Ключ повтора, пользователь, операция, отпечаток параметров и квитанция успешного изменения |
| Audit и Outbox | У1 | Записи об изменениях и события для интеграции, сохранённые в одной транзакции с бизнес-данными |

Путь мероприятия: submitted → approved → preparing → ongoing → completed → archived. Подача предложения сразу ставит его в очередь рассмотрения. Отклонение из submitted переводит в rejected с причиной. Отмена из submitted, approved, preparing или ongoing переводит в cancelled с причиной. Отклонение и отмена — терминальные исходы.

Состояния approved, preparing, ongoing, completed и archived требуют одного ответственного. В БД это один обязательный столбец, а не набор флагов у участников. Передача ответственности меняет его атомарно и активирует участие нового ответственного. Старая роль ответственного перестаёт давать управление сразу после передачи.

Задание создаётся в assigned. Исполнитель может перейти в in_progress, needs_help или done; needs_help требует пояснения и сохраняет исполнителя. done и cancelled терминальны. Ответственный или координатор может переназначить незакрытое задание либо отменить его с причиной. При переназначении состояние становится assigned. Бывший исполнитель больше не управляет заданием.

## Доступ и команды

У3 передаёт внутренний actor_id, полученный из проверенного сообщения или сессии. Модуль каждый раз запрашивает IdentityDirectory и запрещает работу неизвестному или недопущенному пользователю. Отсутствие провайдера регистрации не включает обход авторизации. Публичного HTTP-интерфейса, доверяющего actor_id из запроса, в модуле нет.

| Действие | Кто выполняет |
| --- | --- |
| Предложить мероприятие и посмотреть свои предложения | Допущенный участник |
| Читать карточку мероприятия | Автор, главный ответственный, активный участник, приглашённый пользователь или координатор; заявитель видит карточку, пока заявка на рассмотрении |
| Очередь рассмотрения и утверждение или отказ | Координатор |
| Приглашение, приём, удаление участника и подбор помощников | Главный ответственный или координатор |
| Подать заявку | Допущенный пользователь с ID мероприятия; это не открывает ему список чужих мероприятий |
| Принять приглашение | Сам приглашённый через команду участия |
| Передать ответственность, изменить этап, назначить или отменить задание | Главный ответственный или координатор |
| Читать задания | Ответственный и координатор видят задания мероприятия; исполнитель — только свои |
| Изменить статус задания | Его текущий исполнитель с активным участием; управленческая роль не позволяет отметить чужую работу выполненной |

Территория и интересы используются для подбора помощников, а не для автоматического раскрытия всех мероприятий. Координаторы территорий и представители советов получают доступ к конкретному мероприятию через явное участие. Подбор доступен только управляющему мероприятием и возвращает минимальные карточки без контактов, возраста и согласий.

Все изменяющие команды требуют request_id. Для изменения существующего объекта клиент передаёт expected_version из последнего чтения. Команда возвращает Receipt с ID ресурса и его версией на момент выполнения; актуальную карточку надо прочитать отдельно.

Повтор одинакового request_id и параметров от того же пользователя возвращает ту же квитанцию без повторного изменения. Другие параметры с тем же ключом вызывают IdempotencyConflict. Проверка текущего допуска и полномочий выполняется до повтора: ранее успешная команда не позволяет обойти отзыв доступа. Ошибочная команда не занимает ключ. Устаревшая версия вызывает Conflict, после которого интерфейс перечитывает карточку и предлагает пользователю повторить решение.

Ошибки модуля: ValidationError для некорректных параметров, Forbidden для запрета доступа, NotFound для недоступного или отсутствующего объекта, Conflict для состояния или версии, IdempotencyConflict для несовместимого повтора. Неавторизованное чтение объекта возвращает NotFound, чтобы не раскрывать его существование.

## Хранилище и согласованность

SQLite хранит мероприятия, участие, задания, команды, журнал и исходящие события. Изменение начинается с BEGIN IMMEDIATE; бизнес-запись, аудит, исходящие события и квитанция фиксируются вместе. Версия предотвращает молчаливое затирание решения другим участником. При исключении все записи команды откатываются.

Транзакции сериализуют записи в одной БД. Ограничение SQLite одним писателем означает, что горизонтальное масштабирование и отдельные сервисы требуют пересмотра хранилища, а не копирования файла на несколько узлов. Миграции применяются явно при инициализации Store; подключения включают внешние ключи. Рабочую БД и её резервные копии нельзя добавлять в Git.

Основания: [транзакции SQLite](https://www.sqlite.org/lang_transaction.html), [модуль sqlite3](https://docs.python.org/3.12/library/sqlite3.html).

## Подключение участников команды

У2 реализует IdentityDirectory: получение текущего допуска по внутреннему ID и поиск кандидатов по территории, интересам и виду помощи. Модуль не хранит пароли, документы согласия или контакты. Провайдер должен использовать актуальные данные без устаревшего кэша полномочий. Для строгой атомарности отзыва в будущем У2 согласует с У1 чтение IAM в той же транзакционной границе; отдельный внешний провайдер не даёт распределённой атомарности сам по себе.

У3 вызывает EventService, ParticipationService и TaskService, обрабатывает ошибки и перечитывает версии. Не следует присылать в модуль роли пользователя из формы или считать скрытую кнопку проверкой доступа.

У4 читает Outbox через Store.pending_messages и подтверждает обработку через acknowledge_message только после внешнего успеха. Это доставка как минимум один раз: сбой после отправки до подтверждения может дать повтор. message_id — стабильный ключ дедупликации потребителя. Несколько отправителей без согласованного механизма захвата не запускаются. Обычные task.changed используются для обновления меню и напоминаний, но не для рассылки в общую координацию.

Перед внешним действием У4 перечитывает актуальное состояние и допуск получателя: старое приглашение не должно вернуть удалённого участника, а событие назначения — напомнить об уже отменённом задании. Получатель event_owner определяется по текущему ответственному. Outbox, его подтверждения и доступ к файлу БД — внутренние интерфейсы доверенного процесса, не методы для публикации пользователю. Отзыв допуска У2 должен отдельно инициировать сверку членства У4, даже если пользователь больше не вызывает команды У1.

Завершение мероприятия требует сохранённого отчёта по данным CompletionReader. При незакрытых заданиях команда отклоняется, пока ответственный не закончит их или явно не задаст причину отмены оставшихся заданий. Архивирование доменного объекта разрешено только после подтверждённой доставки итогов и реального архива чата. Отсутствующие подтверждения означают отказ операции; один флаг из пользовательской формы не считается подтверждением.

У5 проверяет модуль на файловой SQLite, включая перезапуск и конкурентные записи. Синтетический пример предоставляет провайдеры регистрации и отчётов только для демонстрации; интеграционная приёмка с реальными модулями У2–У4 остаётся отдельной задачей.

## Демонстрационные сценарии и приёмка У1

1. Участник предлагает мероприятие; координатор видит его в очереди, утверждает и назначает ответственного. Повтор команды не дублирует объект; отказ требует причины.
2. Ответственный находит кандидата, приглашает его; участник принимает приглашение. Посторонний не получает сведения. Передача ответственности не оставляет двух ответственных, устаревшая конкурентная запись отклоняется.
3. Ответственный назначает задание. Исполнитель просит помощь и завершает работу; запрос помощи попадает в очередь для ответственного, а обычный статус не вызывает сообщение в координацию.
4. Сохранённый отчёт разрешает завершение; доставка и архив чата разрешают архивирование. Открытые задания требуют отдельного решения, а недоступная интеграция не выдаёт успех.
5. Повтор после перезапуска возвращает прежнюю квитанцию. Отзыв допуска, передачи полномочий, чужие ID и ошибки транзакций не дают обхода прав или частичных записей.
