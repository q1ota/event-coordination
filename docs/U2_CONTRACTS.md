# У2 — Регистрация пользователей и управление доступом

## Назначение модуля

Модуль обеспечивает регистрацию пользователей, хранение профилей,
управление согласиями, назначение ролей, разграничение полномочий
и взаимодействие с другими компонентами системы.

Реализованы основные механизмы задач T06–T10.

## Структура модуля

Модуль расположен в `event_coordination/identity/`.

| Файл | Назначение |
| --- | --- |
| models.py | Модели пользователей, статусы и роли |
| repository.py | Работа с SQLite и управление транзакциями |
| schema.sql | Структура базы данных |
| registration.py | Регистрация и заполнение профилей |
| authorization.py | Назначение, отзыв и проверка ролей |
| scopes.py | Разграничение областей полномочий |
| admission.py | Проверка согласий и предоставление допуска |
| directory.py | Взаимодействие с модулем У1 |
| external.py | Привязка внешних идентификаторов |

## T06. Регистрация и профили пользователей

Регистрация выполняется по идентификатору Telegram.
Каждому пользователю присваивается уникальный внутренний
идентификатор UUID.

Профиль пользователя содержит:

- имя;
- идентификатор Telegram;
- внутренний идентификатор;
- возраст;
- территорию;
- интересы;
- виды помощи;
- статус регистрации;
- время создания и обновления.

Повторная регистрация с одинаковым идентификатором Telegram
не создаёт новую запись.

Территории и направления деятельности хранятся в отдельных
справочниках.

Согласия с правилами и обработкой персональных данных сохраняются
с указанием версии документа и времени принятия.

Незаполненная анкета не предоставляет рабочий доступ.

### Статусы регистрации

| Статус | Описание |
| --- | --- |
| draft | Анкета находится на этапе заполнения |
| pending | Анкета отправлена на проверку |
| active | Пользователь допущен к работе |
| rejected | В регистрации отказано |
| revoked | Допуск пользователя отозван |

### Основные операции

| Метод | Назначение |
| --- | --- |
| start_registration | Создание или получение существующего профиля |
| update_profile | Заполнение анкеты |
| accept_consent | Сохранение согласия |
| submit_registration | Проверка и отправка анкеты |
| get_profile | Получение профиля |
| add_territory | Добавление территории |
| add_direction | Добавление направления деятельности |

## T07. Роли и авторизация

В системе предусмотрены следующие роли:

| Роль | Назначение |
| --- | --- |
| participant | Участник |
| event_responsible | Главный ответственный за мероприятие |
| territory_coordinator | Координатор территории |
| council_representative | Представитель профильного совета |
| general_coordinator | Общий уполномоченный координатор |
| tech_admin | Технический администратор |

Назначение и отзыв ролей выполняются с проверкой полномочий
действующего пользователя.

Самостоятельное назначение ролей запрещено.

Технический администратор не получает организационных
полномочий автоматически.

Пользователи без действующего допуска не могут использовать
назначенные им роли.

Все успешные изменения ролей записываются в журнал аудита.
При отзыве роли сохраняется история её назначения и отзыва.

До согласования окончательной политики выдача ролей
по умолчанию отключена.

### Основные операции

| Метод | Назначение |
| --- | --- |
| resolve_actor | Определение внутреннего ID по Telegram ID |
| has_role | Проверка действующей роли |
| grant_role | Назначение роли |
| revoke_role | Отзыв роли |
| list_roles | Получение списка действующих ролей |

## T08. Области полномочий

Для отдельных ролей предусмотрена область действия.

| Роль | Область действия |
| --- | --- |
| territory_coordinator | Конкретная территория |
| council_representative | Конкретное направление |
| event_responsible | Конкретное мероприятие |

Один пользователь может совмещать несколько ролей и иметь
несколько областей полномочий.

Наличие полномочий в одной области не предоставляет
автоматический доступ к другим областям.

При отзыве роли в определённой области остальные действующие
роли пользователя сохраняются.

Перед назначением роли проверяется существование территории,
направления или мероприятия.

Для проверки существования мероприятия используется функция
`event_exists`, передаваемая через `ScopePolicy`.

Если интеграция с мероприятиями не настроена, назначение
соответствующей роли запрещается.

Управление самим мероприятием дополнительно проверяется
модулем У1.

### Основные операции

| Метод | Назначение |
| --- | --- |
| can_manage_territory | Проверка полномочий в территории |
| can_manage_direction | Проверка полномочий в направлении |
| can_manage_event | Проверка роли для мероприятия |

## T09. Родительское согласие и допуск

Реализован механизм подачи заявки на проверку родительского
согласия, подтверждения, отклонения и отзыва согласия.

Возрастной порог и версии необходимых согласий задаются
через `AdmissionPolicy`.

### Статусы родительского согласия

| Статус | Описание |
| --- | --- |
| pending | Согласие ожидает проверки |
| verified | Согласие подтверждено |
| rejected | Согласие отклонено |
| revoked | Согласие отозвано |

Предоставление допуска выполняется после проверки анкеты
и необходимых согласий.

Для пользователя, которому требуется родительское согласие,
допуск невозможен без его подтверждения.

Подтверждённое родительское согласие само по себе
не предоставляет рабочий доступ.

При одобрении регистрации пользователь получает статус
active и роль participant.

При отзыве допуска действующие роли пользователя отзываются
в той же транзакции.

При отзыве родительского согласия у допущенного пользователя
его доступ блокируется.

Решения о допуске и согласиях записываются в журнал аудита.

Реальные документы родителей в текущей реализации не хранятся.
Проверка личности родителя, форма согласия и порядок хранения
документов требуют отдельного согласования.

### Основные операции

| Метод | Назначение |
| --- | --- |
| submit_parental_consent | Создание заявки на проверку согласия |
| review_parental_consent | Подтверждение или отклонение согласия |
| approve_registration | Предоставление допуска |
| reject_registration | Отказ в регистрации |
| revoke_access | Отзыв рабочего доступа |
| revoke_parental_consent | Отзыв родительского согласия |

## T10. Автономность и интеграция

Модуль регистрации не зависит от наличия сторонних
информационных систем.

Внутренний идентификатор пользователя сохраняется независимо
от привязки внешних идентификаторов.

Для взаимодействия с модулем У1 реализован класс
`SQLiteIdentityDirectory`, соответствующий интерфейсу
`IdentityDirectory` из `event_coordination/contracts.py`.

### Интерфейс взаимодействия с У1

| Метод | Назначение |
| --- | --- |
| get | Получение актуальных сведений о пользователе |
| candidates | Подбор допущенных пользователей по заданным критериям |

Другим модулям передаются следующие сведения:

- внутренний идентификатор;
- отображаемое имя;
- статус допуска;
- признак общих полномочий координатора;
- территория;
- интересы;
- виды помощи.

Возраст, Telegram ID и сведения о согласиях через
IdentityDirectory не передаются.

Информация о статусе допуска не кешируется.
При следующем обращении после отзыва допуска модуль У1
получает обновлённый статус пользователя.

Глобальное полномочие can_coordinate предоставляется
только действующему общему координатору.

### Внешние идентификаторы

Класс `ExternalIdentityService` предусматривает возможность
будущей интеграции с внешними информационными системами.

| Метод | Назначение |
| --- | --- |
| link | Привязка внешнего идентификатора |
| resolve | Получение внутреннего идентификатора |
| unlink | Удаление привязки |

Один внешний идентификатор не может принадлежать
нескольким пользователям.

Привязка или удаление внешнего идентификатора не изменяет
основной внутренний идентификатор пользователя.

Привязка внешних идентификаторов по умолчанию отключена.

Перед подключением реальной внешней системы необходимо
согласовать процедуру подтверждения принадлежности аккаунта.

## Хранение данных

Для хранения данных используется SQLite.

| Таблица | Назначение |
| --- | --- |
| territories | Справочник территорий |
| directions | Справочник направлений |
| users | Профили пользователей |
| user_interests | Интересы пользователей |
| user_help_types | Виды помощи |
| consents | Согласия пользователей |
| user_roles | Назначенные и отозванные роли |
| authorization_audit | Журнал изменений доступа |
| parental_consents | Родительские согласия |
| external_identities | Внешние идентификаторы |

Связанные изменения выполняются в транзакциях.
Соединения с базой данных закрываются после завершения операций.

Для текущей реализации используется отдельная база данных У2.

Рабочие базы данных и реальные персональные данные
не включаются в репозиторий.

## Совместная работа У1 и У2

Сквозной интеграционный тест проверяет следующий сценарий:

1. Регистрация пользователя через У2.
2. Подтверждение регистрации координатором.
3. Создание мероприятия через У1.
4. Одобрение мероприятия координатором.
5. Отзыв допуска пользователя через У2.
6. Запрет дальнейшего доступа пользователя к мероприятию.

Сценарий успешно проходит автоматическое тестирование.

## Ограничения и открытые вопросы

- D03: окончательные возрастные ограничения, форма родительского
  согласия, проверка личности родителя, хранение и удаление данных.
- D04: назначение первого координатора и утверждение политики
  выдачи и отзыва ролей.
- Подключение доверенного источника Telegram ID.
  Идентификатор действующего пользователя не должен поступать
  из произвольного пользовательского ввода.
- Согласование общего механизма хранения и миграций с У1.
- Согласование транзакционной границы между базами У1 и У2.
  Последовательные операции используют актуальный статус допуска,
  но единой транзакции между модулями пока нет.
- Согласование полномочий территориальных координаторов,
  представителей советов и ответственных с правилами У1.
- Обновление и отзыв обязательных согласий после предоставления допуска.
- Определение сроков хранения и порядка удаления персональных данных.
- Подтверждение принадлежности внешних аккаунтов перед включением
  соответствующей интеграции.

В автоматических тестах используется условный возрастной порог
18 лет и искусственные версии согласий.

Тестовая политика не является утверждённой рабочей политикой.
До согласования открытых вопросов механизмы назначения ролей,
проверки допуска и внешней привязки не должны включаться
в рабочей среде без соответствующей настройки.
