# У2 — регистрация пользователей и управление доступом

Модуль `event_coordination/identity/` реализует задачи T06–T10. Инструкция по подключению к У1, У3 и У4: [U2_INTEGRATION.md](U2_INTEGRATION.md).

## 2. T06 — регистрация

Профиль содержит внутренний UUID, Telegram ID, имя, территорию (регион и населенный пункт), дату рождения или возраст, интересы, виды помощи, статус и время создания/обновления. Бот использует дату рождения. Повторный запуск регистрации с тем же Telegram ID возвращает существующую запись. Для отправки анкеты необходимы заполненные поля и актуальные согласия `rules` и `personal_data`.

| Статус | Значение |
|---|---|
| `draft` | Заполнение анкеты |
| `pending` | Ожидание решения координатора |
| `active` | Регистрация подтверждена; рабочий доступ дополнительно проверяется |
| `rejected` | Отказ в регистрации |
| `revoked` | Допуск отозван |

Возрастная политика `AgePolicy`: минимум 12 лет, родительское согласие в 12–15 лет, самостоятельная регистрация с 16 лет, координаторские роли с 18 лет. Возраст по дате рождения пересчитывается при проверке. Возрастные пороги настраиваются. Допуск всех пользователей требует решения координатора. Настройки запуска описаны в инструкции интеграции.

Справочники заполняются доверенным оператором через `RegistrationService.add_territory(territory_id, region, locality)` и `add_direction(direction_id, name)`. Интересы выбираются из справочника направлений; виды помощи — непустые строки. Редактирование анкеты доступно в статусе `draft`.

## 3. T07 — роли и авторизация

| Роль | Область |
|---|---|
| `participant` | Участник, глобальная роль |
| `general_coordinator` | Общая координация, глобальная роль |
| `territory_coordinator` | ID территории |
| `council_representative` | ID направления |
| `event_responsible` | ID мероприятия |
| `tech_admin` | Техническая роль, без автоматических организационных полномочий |

Назначение и отзыв ролей выполняет допущенный общий координатор; выдача ограничена `grantable_roles`. Самоназначение запрещено. Первого общего координатора назначает доверенный оператор через `BootstrapService`. Операция одноразовая, даже если впоследствии все координаторы потеряли доступ. Назначения и отзывы сохраняются в аудите.

При каждом рабочем действии проверяются статус, возрастная политика, актуальность обязательных и необходимых родительских согласий. Отозванная роль не дает полномочий. Telegram ID извлекается транспортом из аутентифицированного обновления, а не из пользовательского текста.

## 4. T08 — области полномочий

`AuthorizationService.has_role` проверяет конкретную роль и область. Методы `can_manage_territory`, `can_manage_direction`, `can_manage_event` проверяют соответствующие назначения. `ScopePolicy` проверяет существование области; для мероприятий нужен доверенный `event_exists`. Совмещение ролей разрешено, права одной области не распространяются автоматически на другие.

`ChatAccessService` проверяет доступ к координационному, территориальному, профильному и рабочему чату мероприятия. Для мероприятия авторитетный источник — У1: текущий ответственный или активный участник рабочего мероприятия. Роль `event_responsible` в У2 сама по себе не заменяет назначение У1. Фактическое членство и отзыв приглашений выполняет У4.

## 5. T09 — согласия, допуск и данные

Обязательные согласия имеют тип, версию и время принятия/отзыва. При смене версии рабочий доступ приостанавливается до принятия актуальных условий. Явный отзыв обязательного согласия у активного пользователя переводит его в `pending` и отзывает роли; повторное принятие требует нового допуска. Прежние роли автоматически не восстанавливаются.

Родительское согласие: ребенок получает одноразовый токен на 24 часа, родитель открывает форму с другого Telegram-аккаунта, указывает степень родства и подтверждает условия. Координатор проверяет заявку и принимает решение. Сохраняются версия, ID аккаунта родителя, степень родства, время отправки, результат, проверяющий и ссылка на факт проверки. ФИО родителя и сканы документов текущий API не принимает. Другой аккаунт не является доказательством родства.

| Статус согласия | Значение |
|---|---|
| `pending` | Ожидание заполнения или проверки |
| `verified` | Подтверждено координатором |
| `rejected` | Отклонено; возможна новая заявка |
| `revoked` | Отозвано |

Подтверждение согласия не заменяет одобрение регистрации. Отзыв родительского согласия координатором блокирует допуск активного пользователя и отзывает его роли. Самостоятельный отзыв родителем через бот не реализован: обращение передается координатору по регламенту.

`PrivacyService` очищает профиль и связанные личные сведения, отзывает роли, разрывает привязки и сохраняет UUID для истории. Повторная регистрация создает новый UUID. Очистка просроченных анкет касается только `draft`; срок по умолчанию 30 дней. Операции доступны доверенному оператору при `erasure_enabled=True`. Это не полное удаление данных из У1, Telegram, журналов SQLite или резервных копий; требуется отдельный порядок для этих хранилищ и данных родителя в чужих заявках.

## 6. T10 — автономность и интеграция

У2 использует отдельную SQLite-базу и работает без внешнего ядра. `SQLiteIdentityDirectory` реализует существующий контракт У1: `get(user_id)` возвращает актуальную карточку или `None`, `candidates(territory_id, interest, help_type)` — допущенных кандидатов. Передаются UUID, отображаемое имя, допуск, глобальное полномочие координации, территория, интересы и виды помощи. Возраст, Telegram ID и согласия не передаются. Допуск не кешируется.

`ExternalIdentityService(repo, linking_enabled=False)` поддерживает будущую привязку внешних аккаунтов:

- `link(actor_id, user_id, provider, external_id, reason=...)` — привязка;
- `resolve(provider, external_id)` — UUID допущенного пользователя или `None`;
- `unlink(actor_id, user_id, provider, reason=...)` — удаление привязки.

Привязка не меняет UUID и не заменяет проверку принадлежности внешнего аккаунта. Включение выполняется только для доверенной интеграции после согласования ее проверки.

## 7. Хранилище

| Таблицы | Назначение |
|---|---|
| `territories`, `directions` | Справочники |
| `users`, `user_interests`, `user_help_types` | Профили и предпочтения |
| `consents`, `consent_history`, `identity_consent_policy` | Обязательные согласия и версии |
| `parental_consents`, `parental_invitations`, `parental_verifications`, `identity_parental_policy` | Родительские согласия, токены и проверки |
| `user_roles`, `authorization_audit` | Роли и аудит |
| `identity_bootstrap` | Первоначальное назначение координатора |
| `external_identities` | Внешние привязки |
| `privacy_erasure` | Журнал очистки |

Связанные изменения У2 выполняются в транзакциях. У1 и У2 используют отдельные базы; общей атомарной транзакции между ними нет. Рабочие базы и реальные персональные данные не включаются в Git.

## 8. Запуск и проверка

```powershell
python -m pip install .
python -m examples.u2_registration
python -m unittest discover -v
```

Демонстрация использует искусственные данные и временную базу. Тесты охватывают регистрацию, роли, области, допуск, интеграцию У1, возраст, bootstrap, gateway, согласия, электронную форму, очистку и доступ к чатам. Фактические результаты фиксируются в PR после запуска. Условия рабочего запуска и обязанности интеграторов приведены в [U2_INTEGRATION.md](U2_INTEGRATION.md).
