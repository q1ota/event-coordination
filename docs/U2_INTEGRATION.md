# У2: подключение регистрации, допуска и чатов

Актуализация контрактов после этапов 1–7. При расхождении с первоначальным
`U2_CONTRACTS.md` используйте этот документ. Внешнее ядро не требуется.

## 1. Конфигурация общего приложения

Один доверенный процесс или согласованная конфигурация процессов должны
использовать один файл IAM SQLite и одинаковые возрастные настройки.
У1 хранит мероприятия в отдельном SQLite-файле. Не передавайте конфигурацию,
доступ к SQLite и локальные административные методы пользователю бота.

```python
from event_coordination.identity.policy import AgePolicy
from event_coordination.identity.admission import AdmissionPolicy
from event_coordination.identity.repository import IdentityRepository
from event_coordination.identity.gateway import IdentityGateway
from event_coordination.identity.directory import SQLiteIdentityDirectory
from event_coordination.identity.models import Role
from event_coordination.identity.chat_access import (
    ChatKind, ChatAccessService, U1EventMembership,
)
from event_coordination.events import EventService
from event_coordination.storage import Store

# Пример тестовой конфигурации, не утвержденные тексты согласий.
ages = AgePolicy(minimum_age=12, parental_consent_age=16,
                 coordinator_minimum_age=18, minors_enabled=False)
policy = AdmissionPolicy(adult_age=ages.parental_consent_age,
                         rules_version="v1", personal_data_version="v1",
                         parental_version="v1")
repo = IdentityRepository("identity.sqlite", age_policy=ages)
# Включение review_enabled и grantable_roles — только после D04.
gateway = IdentityGateway(repo, policy=policy)
directory = SQLiteIdentityDirectory(repo)
store = Store("events.sqlite")
events = EventService(store, directory)
access = ChatAccessService(repo, event_member=U1EventMembership(store))
```

`adult_age` в существующем AdmissionPolicy означает порог родительского
согласия, а не юридическое совершеннолетие. Он должен совпадать с
`parental_consent_age`. Возраст считается по дате рождения; старый интерфейс
с числовым возрастом сохранен для совместимости, но не используется ботом.
До утверждения D03 `minors_enabled=False`. Не использовать legacy-вызовы
без AgePolicy/опубликованных версий для боевого доступа. Конфигурация
возраста должна быть согласована между всеми процессами; она не является
автоматически распространяемой настройкой в БД. Изменение порогов требует
проверки уже допущенных пользователей. Тексты v1 — синтетические примеры.

## 2. У3: доверенный источник личности

Транспорт бота аутентифицирует источник обновления (long polling либо
проверенный webhook). Берет `sender_id` из `message.from_user.id` или
`callback_query.from_user.id` (в зависимости от библиотеки), а не из
текста, payload кнопки, username, chat_id или произвольного UUID.
При отсутствии достоверного отправителя операция отклоняется. Анкета и
согласия обрабатываются в личном диалоге. Сам IdentityGateway не проверяет
подлинность сетевого запроса: это граница доверенного процесса.

Для всех методов ниже первый позиционный аргумент — доверенный `sender_id`.
Владелец собственной анкеты определяется автоматически. `target_id` в
административных методах — внутренний UUID объекта действия, не личность
исполнителя. Не передавать роли, причины или решения в обход проверок.

| Метод IdentityGateway | Дополнительные параметры | Результат |
|---|---|---|
| `start_registration` | — | UserProfile; повтор не создает дубль |
| `get_my_profile` | — | Собственный UserProfile |
| `update_my_profile` | display_name, territory_id, birth_date (`datetime.date`), interests, help_types | UserProfile |
| `accept_my_consent` | consent_type (`rules` / `personal_data`), version | Принятие обязательного согласия |
| `submit_my_registration` | — | UserProfile со статусом pending |
| `withdraw_my_consent` | consent_type | bool; отзыв и блокировка допуска |
| `resolve_actor` | — | UUID допущенного пользователя |
| `approve_registration` | target_id, reason | Подтверждение допуска |
| `reject_registration` | target_id, reason | Отказ |
| `revoke_access` | target_id, reason | Отзыв допуска |
| `grant_role` | target_id, role, scope_id (по умолчанию пустой), reason | ID назначения |
| `revoke_role` | target_id, role, scope_id (по умолчанию пустой), reason | bool |
| `list_my_roles` | — | Назначения ролей |

Обязательные согласия показываются раздельно, с действующими утвержденными
текстами и версиями, до соответствующего подтверждения. Пользователю с
неактуальными согласиями нужно оставить доступ к обновлению согласий и
своему профилю, но не к рабочим действиям. После явного отзыва обязательного
согласия требуется повторное подтверждение допуска; прежние роли не
восстанавливаются автоматически. При обычной смене версии неотозванные
роли приостанавливаются до принятия актуальных условий.

`resolve_actor` вызывается для каждого рабочего действия, а не один раз
при входе в меню. Для У1 передается возвращенный UUID. `pending` не дает
рабочего допуска. Не считать `active` в профиле достаточным: фактический
допуск также зависит от текущих согласий и возрастной политики.

## 3. Электронное родительское согласие

Предлагаемый сценарий (D03 еще не утвержден): 12–15 лет — согласие родителя,
16–17 — самостоятельная регистрация при утвержденной политике, до 12 лет
нельзя завершить анкету; координаторские роли с 18 лет.

1. Ребенок завершает анкету, принимает обязательные согласия и отправляет
   регистрацию на рассмотрение.
2. `gateway.issue_parental_invitation(child_sender)` возвращает токен.
   У3 формирует ссылку `https://t.me/<bot_username>?start=<token>`.
   Токен содержит 43 URL-safe символа, не является UUID или открытым ID
   ребенка; не логировать его. Срок действия — 24 часа, новая выдача
   заменяет старое неотправленное приглашение.
3. Родитель открывает ссылку со своего аккаунта. У3 передает его собственный
   доверенный ID и токен в `open_parental_form(parent_sender, token=token)`.
   Возвращаются `version` и `expires_at`. Открытие не расходует токен.
4. У3 показывает утвержденный текст и собирает ответы. Отправка:

```python
consent_id = gateway.submit_parental_form(
    parent_sender, token=token, version=version,
    relationship="mother",  # father / legal_guardian
    confirms_guardianship=True,
    accepts_participation=True,
    accepts_data_terms=True,
)
```

Все три подтверждения должны быть явно получены, а не установлены ботом
автоматически. Текущий API не принимает ФИО родителя: сохраняются ID его
аккаунта, тип родства, время отправки, версия, результат проверки; при
необходимости ФИО/доказательства потребуется согласованное расширение.
Токен после отправки повторно не используется. Родитель не обязан иметь
зарегистрированный профиль участника.

5. У3 доставляет запрос уполномоченному координатору. Серверный метод
   `get_parental_review_details(coordinator_sender, consent_id=consent_id)`
   возвращает сведения заявки для проверки. Уведомления и очередь
   административного интерфейса в У2 не реализованы; требуется У3/У4
   согласовать доставку, повтор и просмотр ожидающих заявок.
6. Координатор проверяет личность и полномочия родителя утвержденным
   организацией способом, затем вызывает:

```python
gateway.review_parental_consent(
    coordinator_sender, consent_id=consent_id, approved=True,
    reason="Verification completed", verification_method="electronic_form",
    verification_ref="REVIEW-123",
)
```

При отказе `approved=False` и понятная причина; подтверждение можно подать
заново после отказа. Ссылка и другой аккаунт Telegram не доказывают родство
или возраст. `verification_ref` — краткая ссылка на факт реально проведенной
проверки, не паспортные данные и не фиктивное подтверждение. Родитель не
может проверять собственную форму как координатор.

7. Для первичной регистрации после подтверждения согласия отдельно вызывается
   `approve_registration(coordinator_sender, target_id=child_uuid, reason=...)`.
   Рабочее меню доступно только после успешного `resolve_actor(child_sender)`.
8. Отзыв: `revoke_parental_consent(coordinator_sender, consent_id=..., reason=...)`.
   Обращение родителя о добровольном отзыве и проверка его личности должны
   быть предусмотрены интерфейсом/регламентом; прямого публичного метода
   самостоятельного отзыва родителем пока нет.

## 4. У1: мероприятия и задания

Существующий `IdentityDirectory` не меняется. `get(user_id)` возвращает
Identity либо None; `candidates(territory_id, interest, help_type)` возвращает
актуально допущенные минимальные карточки. Не передаются дата рождения,
Telegram ID, родительские данные или документы. У1 остается источником
истины для участия и главного ответственного. У2 не ограничивает возраст
главного ответственного У1: это потребует расширения контракта по решению
команды. У1 и У2 читают отдельные БД; проверка и операция У1 не имеют общей
атомарной транзакции. При отзыве доступа ответственного/исполнителя нужно
организационно переназначить открытые работы средствами У1.

## 5. У4: права на чаты и сверка членства

```python
allowed = access.can_access(user_uuid, ChatKind.EVENT, event_id)
allowed_for_sender = access.can_access_sender(sender_id, ChatKind.TERRITORY, "kazan")
```

`can_access` принимает доверенный внутренний UUID. `can_access_sender`
принимает доверенный Telegram ID. Оба возвращают bool. Передавать реальные
внутренние идентификаторы территорий, направлений и мероприятий, не имена
и не chat_id. Не передавать произвольный callback из пользовательского ввода.

| ChatKind | scope_id | Условие |
|---|---|---|
| COORDINATION | пустая строка | Общий координатор или явно подтвержденное право |
| TERRITORY | ID территории | Роль координатора данной территории или подтвержденное право |
| COUNCIL | ID направления | Роль представителя данного совета или подтвержденное право |
| EVENT | ID мероприятия | У1: текущий ответственный или активный участник рабочего мероприятия |

`confirmed_access(user_id, kind, scope_id) -> bool` — необязательный
доверенный источник дополнительных подтвержденных прав на первые три
категории. У4 должен согласовать и реализовать источник таких назначений;
фактическое нахождение в Telegram-группе не является доказательством права.
Для EVENT источником является `U1EventMembership(store)`; заявка, приглашение
или scoped-роль У2 без активного участия недостаточны. Архивные чаты требуют
отдельной согласованной политики. Никаких прав из профиля по интересам или
территории автоматически не возникает.

У4 хранит привязку внутренних объектов к Telegram chat_id и реестр членств.
Перед приглашением, подтверждением вступления и обработкой повторной операции
проверяет право снова. При отказе прекращает приглашение. Регулярно сверяет
текущих участников и открытые приглашения с актуальными правами; при отзыве
удаляет лишнее членство/инвайт и фиксирует фактический результат Telegram API.
При ошибке не считать операцию успешной, предусмотреть повтор. Не полагаться
только на действия пользователя: его доступ мог быть отозван вне Telegram.
В текущем У2 нет отдельного outbox для отзыва допуска. До согласования
событийного контракта обязательна сверка У4. Между проверкой и внешним
действием возможна гонка, поэтому требуется повторная сверка. Удаление
профиля У2 разрывает Telegram-привязку; У4 должен хранить достаточно данных
для отзыва существующих членств до удаления в рамках согласованного срока.

## 6. Доверенный оператор и настройки

Первый координатор: `BootstrapService(repo, policy=policy).initialize(
telegram_user_id, operator_ref=..., reason=...)` после заполнения и подачи
анкеты и проверки уполномоченным лицом. Это одноразовая локальная операция,
не команда Telegram. CLI: `python -m event_coordination.identity.bootstrap --help`.
Повторная инициализация запрещена даже при потере всех координаторов.
D04 определяет назначающее лицо, разрешенные роли и восстановление доступа.
Пользователь имеет право отозвать согласие даже будучи последним координатором.

Для публикации новых утвержденных версий используются локальные
`ConsentService(repo, policy=policy).publish_policy(operator_ref=...)` и
`ParentalPolicyService(repo, policy=policy).publish_policy(operator_ref=...)`.
Обновить конфигурацию всех процессов согласованно; публикация двух политик
не является одной атомарной операцией. Не менять тексты под прежней версией.

`PrivacyPolicy(draft_retention_days=30, erasure_enabled=False)` — предложенные
настройки. Доверенный оператор после проверки оснований хранения может
включить разрешение и вызвать `PrivacyService(repo, policy=privacy_policy)`:
`erase_user(user_uuid, operator_ref=...)` либо
`purge_expired_drafts(operator_ref=...)`. Чистятся только просроченные draft,
не pending/active. UUID сохраняется как обезличенная в IAM запись; повторная
регистрация создает новый UUID. Это не гарантирует удаление всех копий данных
в У1, Telegram, аудитах, SQLite-журналах и резервных копиях. В частности,
отдельно нужен порядок удаления данных родителя, отправлявшего форму для
другого пользователя. Не включать очистку до утверждения D03.

## 7. Ошибки, проверки и открытые вопросы

- `ValueError`: некорректный ввод, устаревшая версия, неподходящее состояние.
- `PermissionError` (включая `AuthorizationError`): действие не разрешено.
- Ошибки хранения/интеграции не интерпретировать как положительное решение.
  Пользователю показывать безопасное сообщение без SQL, токенов, чужих UUID
  и деталей чужих профилей; оператору — очищенную диагностику.
- D03: возраста, тексты, подтверждение родительства, доказательства, сроки
  хранения и правила участия несовершеннолетних еще требуют утверждения.
- D04: назначающие лица, политика выдачи ролей и аварийное восстановление.
- У3: привязка проверенного отправителя, диалоги, обработка административных
  запросов, доставка статусов. У4: реальные чаты, отзыв членств, архивы.
- Строгая общая транзакция У1/У2, проверка возраста ответственного и возрастные
  ограничения отдельных мероприятий не входят в эти изменения.
